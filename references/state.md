# Local state layout

Everything lives under one `kg-trainer-data/` directory, resolved once by `scripts/paths.py` (run it on its own to print the answer):

1. `$KG_TRAINER_HOME`, if set (absolute or `~`-relative).
2. Otherwise walk up from the working directory and stop at the first directory that either already contains `kg-trainer-data/` or is a git root; the store is `kg-trainer-data/` there.
3. Otherwise `kg-trainer-data/` in the working directory.

So the store follows the project, not the machine, and running from a subdirectory reuses the project's store instead of starting an empty one. The scripts exit rather than resolve to a store inside the skill's own directory — only an explicit `$KG_TRAINER_HOME` can put it there.

Inside a git repo the store must be ignored: it holds bodyweight history, plans and possibly an `<app>-key` file. The scripts print a warning on stderr when it is not; add `kg-trainer-data/` to that repo's `.gitignore` before writing anything.

```
kg-trainer-data/
  profile.json               intake answers, current targets, and the Active App (`app` block)
  <app>-key                  optional, chmod 600 (liftosaur-key, hevy-key) — only if the user asks to save it
  exercise-muscles.json      optional — the user's custom exercises -> primary muscle, layered over references/exercise-muscles.json
  exercise-map-<app>.json    optional — canonical exercise name -> that app's title/id, layered over the Adapter's own map (Hevy reads exercise-map-hevy.json)
  hevy-exercise-templates.jsonl   Hevy's exercise catalogue, cached by `hevy.py sync-catalogue` (Hevy only)
  weight-log.csv             date,weight_kg,fat_percent,waist_cm
  checkins.jsonl             one append-only record per weekly check-in
  data/
    workouts.jsonl           the Workout Log: every logged workout, weights in kg, titles are Canonical Exercise Names (scripts/app.py pull)
    measurements.json        bodyweight, one row per day: [{"date", "weight_kg"}]
    sync.json                {"last_pull": ISO} — when the cache was last refreshed
    free-exercise-db.json    cached photo catalog for the dashboard
  plans/
    meso-01.plan.json        the Canonical Plan: the source of truth, authored by the coach, advanced by plan.py progress
    meso-01.md               the readable plan, generated by `plan.py render`; never hand-edited
    meso-01.liftoscript      optional: the compiled text last sent to Liftosaur (an output, never an input); older stores may hold only this
  dashboard/
    index.html  data.js  img/    generated; opens from disk, contains no API key
```

`data/` (and the Hevy catalogue) is a cache and is replaced wholesale by every `app.py pull`. `profile.json`, `weight-log.csv`, `checkins.jsonl`, `plans/` and the personal exercise maps are the irreplaceable part — they are the only record of what was decided and why.

## profile.json

```jsonc
{
  "name": "Kieffer",
  "age": 28,
  "sex": "male",                    // needed for BMR; ask, never infer from the name
  "height_cm": 178,
  "weight_kg": 82.0,
  "discipline": "bodybuilding",     // powerlifting | bodybuilding | endurance | hybrid
  "experience": "3 years consistent",
  "sessions_per_week": 4,
  "session_minutes": 70,
  "goal": "build muscle, slight fat loss",
  "goal_rate_kg_per_week": -0.15,   // signed: negative loses, positive gains
  "equipment": "full commercial gym",
  "injuries": [
    { "site": "right shoulder", "note": "impingement on flat barbell pressing",
      "avoid": ["flat barbell bench"], "prefer": ["low-incline DB press", "neutral-grip"] }
  ],
  "daily_activity": "desk job, ~7k steps",   // drives the TDEE multiplier
  "current_lifts": { "squat": "120x6", "bench": "80x8", "deadlift": "150x5" },
  "app": { "name": "liftosaur", "key_source": "env", "program_id": "..." },
  "targets": { "calories": 2800, "protein_g": 175, "carbs_g": 355, "fat_g": 75,
               "set_on": "2026-09-18", "basis": "observed_tdee" },
  "created": "2026-09-18",
  "updated": "2026-09-18",
  "last_checkin": "2026-09-18"
}
```

Write it at the end of Phase 1 and update `targets`/`weight_kg`/`updated`/`last_checkin` at every check-in. `weight_kg` holds the current 7-day average, not the most recent single weigh-in — the raw readings live in `weight-log.csv`. `app` is the Active App, written by `app.py use <name>`; `app.py push` records the app's plan id as `app.program_id`, which `app.py update --id` takes. `key_source` records *where* the key came from (`env`, `dotenv` or `file`) — never store the key value in `profile.json`. `app.py use <other>` replaces the block and drops the old `program_id`; a store written before the Adapters has a `liftosaur` block, which the next script to read `profile.json` migrates to `app` once.

## checkins.jsonl

One JSON object per line, appended by `scripts/checkin.py record`:

```jsonc
{"date":"2026-09-18","avg_weight_kg":81.83,"prev_avg_weight_kg":82.14,
 "rate_kg_per_week":-0.314,"calories":2800,
 "macros_g":{"protein":175,"carbs":355,"fat":75},
 "sessions_completed":3,"sessions_planned":4,
 "notes":"bench RPE 8->9.5 at same load; backed off to 72.5"}
```

Append only. Never rewrite a past record — a wrong past decision is data about the client, and overwriting it destroys the trend the whole check-in loop depends on.

## plans/meso-NN.plan.json

The Canonical Plan (schema in `docs/superpowers/specs/2026-11-07-app-agnostic-adapters-spec.md`, checked by `plan.py validate`). Two fields are state rather than design:

- `current_week`: the week the Active App currently shows. `plan.py progress` advances it when the week's rules fire; `app.py compile`, `check` and `update` use it (Hevy compiles only this week; the drift guard compares this week).
- `week_started`: optional `YYYY-MM-DD`, written by `progress` as the day after the last session it counted. The next `progress` ignores sessions before it, so no session is counted twice.

`plan.py progress` rewrites this file in place and `render` regenerates `meso-NN.md`. Nothing else edits a plan except the coach, on a change the athlete approved.

## API key handling

The key for app `<app>` is read from `$<APP>_API_KEY` first (`LIFTOSAUR_API_KEY`, `HEVY_API_KEY`), then from the nearest `.env` (searching the working directory and its parents), then from `kg-trainer-data/<app>-key`. Liftosaur's API needs a premium subscription and Hevy's needs Pro; a 401 from an otherwise correct key usually means it has lapsed. Only write `kg-trainer-data/<app>-key` if the user explicitly asks to save it, and then `chmod 600` it immediately and confirm `kg-trainer-data/` is gitignored: the store sits inside the working directory, so an unignored key file is one careless commit away from leaking. Never echo the key back, never paste it into a plan file, a markdown document, a commit, or an external app. When a key fails, report the HTTP status, not the key.
